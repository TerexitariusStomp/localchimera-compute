# Upstream Issues to Report

_Bugs and improvements discovered deploying Guix System to Hetzner Cloud, 2026-03-28._

---

## 1. Newer Hetzner x86 server types boot UEFI, not BIOS

**Where:** `(gnu machine hetzner)` — `%hetzner-os-x86`, `hetzner-machine-bootstrap-os-form`

**Problem:** The docs and code assume x86 Hetzner servers use BIOS boot mode.
`%hetzner-os-x86` uses `grub-bootloader` targeting `/dev/sda`. But newer server
types (cpx22, cpx32, cx23, cx33, etc.) use TianoCore UEFI firmware. The system
installs fine but GRUB drops to `grub rescue>` with:

```
error: file '/boot/grub/x86_64-efi/normal.mod' not found.
```

**Fix:** `%hetzner-os-x86` should use `grub-efi-bootloader` with target
`/boot/efi`, or the module should detect the firmware type from the server
metadata. The `/dev/sda15` EFI System Partition already exists on the Hetzner
disk image.

**Affected:** Anyone deploying to cpx22, cpx32, cx23, cx33, or newer x86 types.

**Workaround:** Use `grub-efi-bootloader` with `(targets '("/boot/efi"))` and
add `/dev/sda15` as a vfat filesystem at `/boot/efi`.

**Related:** The partition table already has both a BIOS boot partition (sda14)
and an EFI System Partition (sda15), so supporting both modes is possible.

## 2. `guix-install.sh` hardcodes `ftpmirror.gnu.org` with no fallback

**Where:** `https://guix.gnu.org/guix-install.sh`, line ~106

**Problem:** The install script sets `GNU_URL="https://ftpmirror.gnu.org/gnu/guix/"`
with no fallback. When `ftpmirror.gnu.org` returns 502 (which it did consistently
on 2026-03-27/28), the entire Hetzner provisioning fails. The script has no retry
logic and no alternative mirrors.

There is a `GUIX_BINARY_FILE_NAME` env var to provide a local binary, but
`hetzner-environment-type` doesn't use it and can't easily pre-download the
binary to the rescue system.

**Fix options:**
- Add `ftp.gnu.org` as a fallback when `ftpmirror.gnu.org` fails
- Try multiple mirrors from the GNU mirror list
- Allow `GNU_URL` to be overridden via environment variable
- Have `hetzner-environment-type` pre-download the binary locally and SCP it

**Affected:** Anyone using `hetzner-environment-type` (or `guix-install.sh`
on any system) when `ftpmirror.gnu.org` is down.

**Workaround:** `sed -i 's|ftpmirror.gnu.org|ftp.gnu.org|g' guix-install.sh`

## 3. Bootstrap OS default GRUB theme requires `librsvg` (no substitute)

**Where:** `(gnu machine hetzner)` — `hetzner-machine-bootstrap-os-form`

**Problem:** The bootstrap OS generated by the hetzner module uses the default
`grub-bootloader` configuration, which includes a graphical theme. This theme
generates `grub-image.png` via `librsvg`. The Guix 1.5.0 binary installed on
the rescue system has no pre-built substitute for `librsvg`, so it tries to
build it locally on the rescue system — which has limited RAM (2-4GB) and
takes hours, often OOMing.

**Fix:** The bootstrap OS should explicitly set `(theme #f)` in the bootloader
configuration. The bootstrap OS only needs to boot once before being replaced
by the real OS config. There's no need for a graphical GRUB theme.

**Affected:** Anyone deploying to server types with <= 8GB RAM (cpx22, cpx32,
cax11, etc.) where `librsvg` can't build from source.

**Workaround:** `(theme #f)` in the bootloader-configuration.

## 4. Store items not synced from bind mount to real `/gnu/store`

**Where:** `(gnu machine hetzner)` — `hetzner-machine-rescue-install-os`

**Problem:** During provisioning, the module bind-mounts `/mnt/tmp/gnu/store`
to `/gnu/store` so the daemon has a place to write. After `guix system init`,
the store items are in `/mnt/tmp/gnu/store` (via the bind mount) but many are
not in `/mnt/gnu/store` (the real on-disk location). When the system boots and
mounts `/dev/sda1` as `/`, it accesses `/gnu/store` which maps to the real
directory — missing most items.

In our case: `/mnt/gnu/store` had 351 items, `/mnt/tmp/gnu/store` had 4911.
The system couldn't boot because critical files (kernel modules, shepherd,
services) were only in the tmp location.

**Fix:** After `guix system init` completes, hardlink all items from
`/mnt/tmp/gnu/store` to `/mnt/gnu/store`:

```bash
cd /mnt/tmp/gnu/store
for item in *; do
    [ ! -e "/mnt/gnu/store/$item" ] && cp -al "$item" "/mnt/gnu/store/$item"
done
```

**Affected:** Everyone using `hetzner-environment-type`. This may be why
some users report servers that provision but don't boot.

## 5. `guix-install.sh` `gnu-store.mount` overrides bind mount

**Where:** `guix-install.sh` creates `/etc/systemd/system/gnu-store.mount`

**Problem:** The hetzner module sets up `mount --bind /mnt/tmp/gnu/store /gnu/store`
before running `guix-install.sh`. But the install script creates a systemd mount
unit for `/gnu/store` which, when activated, overrides the bind mount. After
install, `/gnu/store` is empty or points to the wrong location. The module then
can't find the `guix` binary to run `guix system init`.

**Fix:** The hetzner module should re-establish the bind mount after
`guix-install.sh` completes:

```bash
umount /gnu/store 2>/dev/null || true
mount --bind /mnt/tmp/gnu/store /gnu/store
```

**Affected:** Everyone using `hetzner-environment-type` on rescue systems
where systemd is running.

---

## 6. `growpart` needed but not always installed

**Where:** `(gnu machine hetzner)` — `hetzner-machine-rescue-partition`

**Problem:** The module installs `cloud-initramfs-growroot` (which provides
`growpart`) in the rescue system. However, the Hetzner Debian 12 disk image
ships with a small root partition (~3.2GB) that needs growing to the full disk.
If `growpart` isn't available or fails silently, `mkfs` creates a tiny filesystem.

This is already handled by the module (PR #4257 added `uidmap` and the
`cloud-initramfs-growroot` was there before), but worth noting that both
packages are essential and the partition MUST be grown before formatting.

**Status:** Likely already fixed in current Guix. Including for completeness.

## 7. Hoot 0.8.0 — `mutable-bytevector?` WASM backend regression

**Where:** `hoot/backend.scm`, `node-within` procedure

**Problem:** `guild compile-wasm` crashes when compiling any module that
transitively references mutable bytevectors (which includes `(goblins)`,
`(srfi srfi-9)`, `(fibers channels)`, and all OCapN modules):

```
hoot/backend.scm:2039:8: In procedure node-within:
Throw to key `match-error' with args
  `("match" "no matching pattern" #(mutable-bytevector? #f (...)))'.
```

**Affected versions:**
- Hoot 0.8.0 (Guix commit `21946173a05869dd40a38012e65b9e35dc47a9fc`)

**Root cause:** Missing `mutable-bytevector?` case in the WASM backend's
`compile-test` match expression. The `$mutable-bytevector` type was added to
`stdlib.scm` between 0.7.0 and 0.8.0, but the predicate dispatch was never
updated to match it.

**Workaround:** We patch `hoot/backend.scm` via `substitute*` in
`deploy/packages/hoot-fix.scm`'s `fix-mutable-bytevector` build phase,
adding the missing match case. This is the workaround that lets us use
Hoot 0.8 at all (rather than rolling back to 0.7).

**Filing:** Should be reported at https://codeberg.org/spritely/guile-hoot.

## 8. Hoot 0.8.0 — `(ice-9 exceptions)` re-exports nonexistent `quit-exception?` / `make-quit-exception`

**Where:** `lib/ice-9/exceptions.scm` in the Hoot source tree
(`guile-hoot-0.8.0/share/guile-hoot/0.8.0/lib/ice-9/exceptions.scm`).

**Problem:** The Hoot stub of `(ice-9 exceptions)` declares
`make-quit-exception` and `quit-exception?` in its `#:re-export` list,
but the underlying module `(hoot exceptions)` does not actually define
either of them. The compile-time path apparently doesn't validate
re-exports against their source modules — wasm bundles built without
the runtime module system (`-g0`, the default `make browser/repl.wasm`
path) compile and run fine because the bindings are simply unused.

The `-g1` and `-g2` paths, which embed the runtime module system to
support live hacking via `(hoot web-repl)`, **do** validate at
module-load time. The first time anything `#:use-module`s
`(ice-9 exceptions)` the loader walks its declared re-exports, hits
`quit-exception?`, finds no underlying binding, and raises:

```
Uncaught exception:
  #<&undefined-variable
       module: #<module (ice-9 exceptions)>
       name: quit-exception?>
  at hoot/errors.scm:95:22
  from hoot/modules.scm:227 module-import!
  from hoot/lists.scm:171 for-each
  from hoot/hackable.scm:79 declare-module!
  from goblins/core-types.scm:23 (use-modules)
```

The wasm fails to instantiate (`SchemeTrapError` from
`reflect.js#init_module`) and the page is blank.

**Affected versions:**
- Hoot 0.8.0 (Guix commit `21946173a05869dd40a38012e65b9e35dc47a9fc`)

**Trigger:** Any wasm bundle built with `-g1` or `-g2` (i.e. the entire
live-hacking workflow described in the 0.8.0 release notes) that imports
`(ice-9 exceptions)` directly or transitively. **Goblins triggers it
immediately** via `goblins/core-types.scm:23` which is loaded the moment
any Goblins-using bundle starts to initialize. In practice this blocks
the Hoot live-REPL workflow for every Goblins app — which is most of
Spritely's own demo surface area.

**Impact:** The new `hoot repl --connect` / `(hoot web-repl)` /
`run-web-repl` workflow advertised in the 0.8.0 release notes does
**not** work for any Goblins-based bundle. It works fine for plain
Hoot examples (the slides demo etc.) which don't import goblins.
The MEMORY note that says "live hacking is wired up end-to-end as of
2026-04-07" is accurate for the *plumbing* (`(hoot web-server)`,
`(hoot web-repl)`, `geiser-hoot`, our `serve-dev` / `weave-dev` make
targets, `tools/live-reload.scm`) — it's only the *one piece in the
middle*, the runtime resolution of `(ice-9 exceptions)`, that's broken.

**Root cause (best guess):** Two adjacent re-export entries in
`lib/ice-9/exceptions.scm` were added in Hoot 0.8 alongside
`&quit-exception`. The author noticed that the type variable
`&quit-exception` doesn't exist in `(hoot exceptions)` and commented
that line out (line 66 in 0.8.0):

```scheme
;; &quit-exception
make-quit-exception
quit-exception?
```

But the predicate and constructor on the next two lines were left
uncommented. They reference bindings that also don't exist in
`(hoot exceptions)` (or anywhere else in the Hoot source tree —
`grep -rn quit-exception lib/` only finds `repl-quit-exception?` in
`hoot/repl.scm`, which is a separately-named type for the REPL
itself). The fix is a one-line patch: comment out both names.

**Workaround (partial):** We patch both lines via `substitute*` in
`deploy/packages/hoot-fix.scm`'s `fix-ice-9-exceptions-quit-exception`
build phase:

```scheme
(substitute* "lib/ice-9/exceptions.scm"
  (("               make-quit-exception\n")
   "               ;; make-quit-exception\n")
  (("               quit-exception\\?\n")
   "               ;; quit-exception?\n"))
```

(Note the `\n` anchors — Guile regex `^`/`$` are string anchors, not
line anchors, and `substitute*` matches against the whole file as one
string.) After applying, `(ice-9 exceptions)` no longer claims to
re-export the missing bindings.

**The patch is necessary but not sufficient.** The first time we hit
this bug (before the patch), the dev wasm printed a clean Hoot
backtrace ending at `make-undefined-variable-error` for
`quit-exception?`. After the patch, the dev wasm **still crashes at
init** but with no Scheme-level backtrace — just a `SchemeTrapError`
from `reflect.js#init_module`. The patch successfully removes the
`quit-exception?` reference, but it exposes some deeper init-time
crash in the runtime module loader that we can't diagnose from the
console output alone (no Scheme backtrace, no source location).

Hypotheses (not yet verified):
1. Removing `quit-exception?` from `(ice-9 exceptions)`'s exports
   silently breaks something downstream that imports it.
2. There are additional broken re-exports in the same file (and/or
   other Hoot ice-9 stubs) that fail the same way.
3. Hoot's runtime module loader has a separate bug that surfaces
   only once `(ice-9 exceptions)` loads cleanly.

For now, **prod (`-g0`) wasm works fine** (the only path our calendar
actually needs), and the rebuild-reload loop (`make browser/repl.wasm`
+ hard reload, ~30s) is the de-facto live-hacking workflow. Real Hoot
0.8 live-REPL hacking via `(hoot web-repl)` remains broken for
Goblins-based bundles until either upstream fixes both layers or we
do a deeper bisect.

**Filing:** Should be reported at
https://codeberg.org/spritely/guile-hoot. The first half is a
two-line fix in upstream `lib/ice-9/exceptions.scm`. The second half
(the silent post-patch crash) needs more investigation before it can
be filed — it'd help to have a minimal reproducer, which we don't
yet have.
