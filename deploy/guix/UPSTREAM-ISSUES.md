# Upstream Issues to Report

_Bugs and improvements discovered deploying Guix System to Hetzner Cloud, 2026-03-28._

---

## 1. Newer Hetzner x86 server types boot UEFI, not BIOS

**Where:** `(gnu machine hetzner)` — `%hetzner-os-x86`, `hetzner-machine-bootstrap-os-form`

**Problem:** The docs and code assume x86 Hetzner servers use BIOS boot mode.
`%hetzner-os-x86` uses `grub-bootloader` targeting `/dev/sda`. But newer server
types (cpx22, cpx32, cx23, cx33, etc.) use TianoCore UEFI firmware. The system
installs fine but GRUB drops to `grub rescue>` with:

```
error: file '/boot/grub/x86_64-efi/normal.mod' not found.
```

**Fix:** `%hetzner-os-x86` should use `grub-efi-bootloader` with target
`/boot/efi`, or the module should detect the firmware type from the server
metadata. The `/dev/sda15` EFI System Partition already exists on the Hetzner
disk image.

**Affected:** Anyone deploying to cpx22, cpx32, cx23, cx33, or newer x86 types.

**Workaround:** Use `grub-efi-bootloader` with `(targets '("/boot/efi"))` and
add `/dev/sda15` as a vfat filesystem at `/boot/efi`.

**Related:** The partition table already has both a BIOS boot partition (sda14)
and an EFI System Partition (sda15), so supporting both modes is possible.

## 2. `guix-install.sh` hardcodes `ftpmirror.gnu.org` with no fallback

**Where:** `https://guix.gnu.org/guix-install.sh`, line ~106

**Problem:** The install script sets `GNU_URL="https://ftpmirror.gnu.org/gnu/guix/"`
with no fallback. When `ftpmirror.gnu.org` returns 502 (which it did consistently
on 2026-03-27/28), the entire Hetzner provisioning fails. The script has no retry
logic and no alternative mirrors.

There is a `GUIX_BINARY_FILE_NAME` env var to provide a local binary, but
`hetzner-environment-type` doesn't use it and can't easily pre-download the
binary to the rescue system.

**Fix options:**
- Add `ftp.gnu.org` as a fallback when `ftpmirror.gnu.org` fails
- Try multiple mirrors from the GNU mirror list
- Allow `GNU_URL` to be overridden via environment variable
- Have `hetzner-environment-type` pre-download the binary locally and SCP it

**Affected:** Anyone using `hetzner-environment-type` (or `guix-install.sh`
on any system) when `ftpmirror.gnu.org` is down.

**Workaround:** `sed -i 's|ftpmirror.gnu.org|ftp.gnu.org|g' guix-install.sh`

## 3. Bootstrap OS default GRUB theme requires `librsvg` (no substitute)

**Where:** `(gnu machine hetzner)` — `hetzner-machine-bootstrap-os-form`

**Problem:** The bootstrap OS generated by the hetzner module uses the default
`grub-bootloader` configuration, which includes a graphical theme. This theme
generates `grub-image.png` via `librsvg`. The Guix 1.5.0 binary installed on
the rescue system has no pre-built substitute for `librsvg`, so it tries to
build it locally on the rescue system — which has limited RAM (2-4GB) and
takes hours, often OOMing.

**Fix:** The bootstrap OS should explicitly set `(theme #f)` in the bootloader
configuration. The bootstrap OS only needs to boot once before being replaced
by the real OS config. There's no need for a graphical GRUB theme.

**Affected:** Anyone deploying to server types with <= 8GB RAM (cpx22, cpx32,
cax11, etc.) where `librsvg` can't build from source.

**Workaround:** `(theme #f)` in the bootloader-configuration.

## 4. Store items not synced from bind mount to real `/gnu/store`

**Where:** `(gnu machine hetzner)` — `hetzner-machine-rescue-install-os`

**Problem:** During provisioning, the module bind-mounts `/mnt/tmp/gnu/store`
to `/gnu/store` so the daemon has a place to write. After `guix system init`,
the store items are in `/mnt/tmp/gnu/store` (via the bind mount) but many are
not in `/mnt/gnu/store` (the real on-disk location). When the system boots and
mounts `/dev/sda1` as `/`, it accesses `/gnu/store` which maps to the real
directory — missing most items.

In our case: `/mnt/gnu/store` had 351 items, `/mnt/tmp/gnu/store` had 4911.
The system couldn't boot because critical files (kernel modules, shepherd,
services) were only in the tmp location.

**Fix:** After `guix system init` completes, hardlink all items from
`/mnt/tmp/gnu/store` to `/mnt/gnu/store`:

```bash
cd /mnt/tmp/gnu/store
for item in *; do
    [ ! -e "/mnt/gnu/store/$item" ] && cp -al "$item" "/mnt/gnu/store/$item"
done
```

**Affected:** Everyone using `hetzner-environment-type`. This may be why
some users report servers that provision but don't boot.

## 5. `guix-install.sh` `gnu-store.mount` overrides bind mount

**Where:** `guix-install.sh` creates `/etc/systemd/system/gnu-store.mount`

**Problem:** The hetzner module sets up `mount --bind /mnt/tmp/gnu/store /gnu/store`
before running `guix-install.sh`. But the install script creates a systemd mount
unit for `/gnu/store` which, when activated, overrides the bind mount. After
install, `/gnu/store` is empty or points to the wrong location. The module then
can't find the `guix` binary to run `guix system init`.

**Fix:** The hetzner module should re-establish the bind mount after
`guix-install.sh` completes:

```bash
umount /gnu/store 2>/dev/null || true
mount --bind /mnt/tmp/gnu/store /gnu/store
```

**Affected:** Everyone using `hetzner-environment-type` on rescue systems
where systemd is running.

---

## 6. `growpart` needed but not always installed

**Where:** `(gnu machine hetzner)` — `hetzner-machine-rescue-partition`

**Problem:** The module installs `cloud-initramfs-growroot` (which provides
`growpart`) in the rescue system. However, the Hetzner Debian 12 disk image
ships with a small root partition (~3.2GB) that needs growing to the full disk.
If `growpart` isn't available or fails silently, `mkfs` creates a tiny filesystem.

This is already handled by the module (PR #4257 added `uidmap` and the
`cloud-initramfs-growroot` was there before), but worth noting that both
packages are essential and the partition MUST be grown before formatting.

**Status:** Likely already fixed in current Guix. Including for completeness.
